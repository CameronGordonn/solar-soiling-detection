# Codebase bug audit — 2026-08-27

Prompted by finding five bugs in a single session of freshly written, carefully reviewed
code. If that rate holds, older code deserves the same scrutiny.

**Scope:** 158 Python files, 9,292 lines in `src/`, 23,378 in `scripts/`.
**Baseline:** 252 tests passing before the audit; **411 passing after** (the new guard test
is parameterised over every file).

**Result: 4 real defects fixed, 1 suspicious pattern investigated and cleared.** All four
were silent — nothing crashed, nothing logged a warning, and the existing tests passed
throughout. That is the common thread and it is the thing to design against.

---

## FIXED — 1. Repo-root path bug, TWO live instances (high severity)

`CLAUDE.md` already records this bug being fixed once in `compare_runs.py`, where
`Path(__file__).parent.parent` resolved to `scripts/` instead of the repo root and the tool
"silently found zero runs". **The same bug was still live in two more files.**

| file | what it broke |
|---|---|
| `scripts/predict/ingest_nrel_soiling_map.py:149` | download and both label CSVs written to `scripts/data/external/` |
| `scripts/predict/build_static_features.py:122` | same, plus `--cache-dir` pointed at `scripts/.cache/soiling` |

Both are in the documented onboarding path in `.claude/rules/stage2-risk.md` under
"One-time ingestion". The ingestion one is the worse of the two: it is the entry point for
`nrel_soiling_map_annual.csv`, the **891-row label set the entire Stage 2 model trains on**.
Re-running it would have written a fresh label set to a directory nothing reads while leaving
the real one stale, with no error.

Fixed to `parents[2]` in both.

**Guard added:** `tests/test_repo_root_resolution.py` walks the AST of every file in `src/`
and `scripts/`, finds any repo-root expression, resolves it, and asserts it lands on a
directory containing `pyproject.toml`, `src/`, `scripts/` and `configs/`. 159 files checked.
This catches the class, not just the two instances.

> The guard test itself shipped with an off-by-one on its first run and flagged 66 correct
> files. `Path(f).parents[N]` is N+1 applications of `.parent`, not N. Fixed and noted in the
> test, because it is the same family of mistake.

## FIXED — 2. Stale calibration defaults (latent, would have been silent)

`.claude/rules/stage2-risk.md` records the SOMOSclean recalibration of 2026-06-01:
`sl_sat` 0.10 → **0.08**, `k` 30 → **15**, fitted to 36 coastal-CA NREL station-years, with
"all four locations updated".

Two more locations still carried the superseded values:

| location | had | should be |
|---|---|---|
| `labels.somosclean_eqd_trajectory` defaults | `sl_sat=0.25, k=30.0` | 0.08, 15.0 |
| `feature_engineering.py:126-127` config fallbacks | `.get("sl_sat", 0.25)`, `.get("k", 30.0)` | 0.08, 15.0 |

**This never fired**, and I verified that rather than assuming: `configs/soiling/features.yaml`
supplies 0.08/15.0, and every in-repo caller passes explicit values
(`physics_score._DEFAULT_PARAMS`, `recovery.DEFAULT_PARAMS`,
`score_alternative_models._SOMOS_PARAMS` all carry 0.08/15.0). But any new caller relying on
the signature default, or any config missing the key, would silently have got **3x the
saturation loss and 2x the time constant** with no error.

Aligned both, with comments recording why.

## FIXED — 3. A false claim in a comment, hiding a 1-point free parameter

`pvdaq_daily_srr_probe.py` set `GAMMA_PDC = -0.0045` with the comment *"Same value the 2107
probe uses."* `washable_share_probe.py` uses **-0.0035**. They have never matched, and I
wrote that comment.

The discrepancy is not cosmetic. Measured on system 10109:

```
gamma = -0.0035  ->  2.841 pts annual soiling loss
gamma = -0.0045  ->  1.796 pts
delta                1.045 pts
```

**That single hardcoded constant has more leverage on a label than the measured method noise
between two independent irradiance sources (SD 0.72), and about as much as the entire
within-cell between-system spread (1.41) that Phase 3 exists to detect.**

Two consequences worth carrying:
1. The 0.72 method-noise figure **excludes** this term and is therefore optimistic.
2. It does not need to be guessed. `pvdaq/csv/system_metadata/<id>_system_metadata.json`
   carries module make and model for all 1,381 residential systems, so the real coefficient
   is lookupable per system.

Kept at -0.0045 so recorded runs stay valid, but documented truthfully and flagged as
unvalidated.

> **CLOSED 2026-08-27.** Resolved per system instead of guessed, from PVDAQ module metadata
> against pvlib's CEC database: 43.3% matched to a named module, 35.2% to a manufacturer,
> 2.0% to a cell technology, 19.6% falling back to a labelled default. Full record in
> [`GAMMA_RESOLUTION_20260827.md`](GAMMA_RESOLUTION_20260827.md).
>
> Three findings. **(1) The recorded labels are biased, not invalidated.** Fleet-resolved
> gamma has median -0.00430 and SD 0.00045, median |delta| from -0.0045 is 0.00020, and only
> 9.0% of systems are 0.0010 or further out. The contrast that raised the alarm was a p91
> excursion. -0.0045 is the CEC median for both Mono-c-Si and Multi-c-Si; **-0.0035 was the
> wrong number**, and PVDAQ publishes no module record for system 2107 to support it.
> **(2) Gamma is a real but secondary noise term**, 26.4% of the two contrasts' variance
> against the irradiance source's 73.6%. **(3) Signal-to-noise falls to 1.76x** from the
> quoted 1.95x, and does not drop below 1.0.
>
> Two estimator corrections found on the way, both of which moved the answer: the old 0.72
> was n=19 with gamma held fixed and the same statistic is 0.78 at n=20; and a single
> corner-to-corner contrast of a 2x2 is not a total-noise estimator, since the two diagonals
> here give 0.72 and 0.92. Both are now handled in `pvdaq_method_noise.py`.
>
> The comment is gone, and `tests/test_module_gamma.py` now fails the suite if anyone writes
> a gamma literal outside `src/risk/module_gamma.py`. The same guard covers `heavy_rain_mm`,
> which was latent in the identical shape: four copies across the tree, each with a comment
> claiming it matched the others.

## INVESTIGATED AND CLEARED — `substring_shade_loss.resample`

`np.interp` clamps rather than extrapolates outside its sampled range, which is exactly the
bug I had just made in `band_soiling.band_loss_pct`. Instrumenting a full run of the
substring physics model showed **47.9% of interpolation points fall outside the sampled range
and are clamped**, one call at 99.9%.

That looked alarming, so I tested whether it moves the answer rather than assuming either
way. Re-running with a **3x finer current grid and 2x finer voltage grid**:

```
scenarios compared: 12
worst change: 0.000 pts
```

**Benign.** The clamping happens in regions the bypass diode dominates, so it cannot reach
the maximum power point. The published 9.10% / 18.39% / 21.00% figures are grid-independent.
No change made.

> **Re-examined 2026-08-27, and this conclusion stands.** `resample` now warns at runtime when
> it is asked to extrapolate, which makes the clamping visible instead of inferred. Re-running
> at n=20 modules reproduces the headline figures exactly (portrait f=0.5 string 21.00% / MLPE
> 8.20%, f=0.2 portrait 9.10%), so nothing quoted moves.
>
> Where the clamping is severest is worth recording, because it explains the mechanism rather
> than just asserting it. At f=1.0 a fully dark cell's IV curve tops out at 1e-4 A while the
> current grid asks for 8 A, so the cell is interpolated as a short rather than a
> reverse-biased blocker. **That is exactly the "bypass diode dominates" region named above**:
> those rows report string loss equal to MLPE loss with no amplification, which is what a
> fully bypassed substring should do. A finer grid could never have detected this, since it
> narrows spacing without widening range, so the two checks are complementary rather than
> redundant. The f=0.1-0.5 band the moss work actually uses is unaffected and still shows the
> amplification (f=0.3 portrait: 4.01% MLPE against 18.39% string).
>
> `SUBSTRING_STRICT_RESAMPLE=1` makes the clamp fatal for anyone extending the model.

## The pattern, and what it suggests

**Every defect found, in this audit and in the session that prompted it, was silent and
optimistic.** Nothing threw. Nothing logged. The test suite passed at every point. The
failure mode is consistently *a plausible wrong number*, not a crash.

Three concrete implications:

1. **Path defaults are the highest-risk silent failure in this repo** — they have now bitten
   three times in the same way. The AST guard closes that class permanently.
2. **A constant duplicated in two places will eventually differ.** Three currently do. The
   fix that actually holds is deriving rather than copying, as was done for `BIO_RECOVERY`
   after it drifted 1.6x within one session.
3. **Sensitivity beats review for free parameters.** `GAMMA_PDC` sat unexamined behind a
   confident comment for as long as it existed; one two-value sweep exposed it as having more
   leverage than the signal. Any hardcoded physical constant should get that sweep before its
   output is quoted.
